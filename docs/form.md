# 問い合わせフォーム仕様

画面は `/form`。質問とサンプルは [src/form/questions.ts](../src/form/questions.ts)、判定の進め方は [src/form/useLiveDecision.ts](../src/form/useLiveDecision.ts)、画面は [src/pages/Form.tsx](../src/pages/Form.tsx)。

## 狙い

「Web システムに組み込んだ例」として、**入力している最中に判定し、フォーム自体がその場で変わる**様子を見せる。
**Jev・Claude Haiku 4.5・Claude Opus 5** が同時に判定し、それぞれ今の入力にどれだけ追いついているかを表示する。
Opus の effort は画面で選べる(既定は速さ優先の low)。

## 判定する内容

state は `{ 問い合わせ本文: <入力中のテキスト> }`。1回のリクエストで4つの質問をまとめて聞く。

| キー | 種類 | 内容 |
|---|---|---|
| `department` | `choice` | 担当部署: 請求・支払い / 技術サポート / アカウント / 配送 / その他 |
| `urgency` | `score` | 緊急度: 急ぎではない / 通常 / 早めの対応が必要 / 今すぐ対応が必要 |
| `refund` | `noul` | 返金や返品を求めているか |
| `angry` | `noul` | 怒っている、または強い不満を持っているか |

## 判定の進め方

- 入力が4文字以上になったら判定を始める
- エンジンごとに、同時に投げるのは1件だけ。判定が返った時点で入力が進んでいれば、**最新の入力ですぐ次を投げる**(途中の入力は飛ばす)
- つまり各エンジンは「自分が出せる最速のペースで入力に追いつこうとする」。速いほど判定回数が増え、遅れが小さくなる
- Opus の effort やダミーモードを切り替えたら判定し直す

## フォームの出し分け

「フォームを動かす判定」で選んだエンジン(Jev / Haiku / Opus、初期値 Jev)の結果を使う。しきい値は `toFormView` にまとめている。

| 条件 | 出るもの |
|---|---|
| 返金の依頼の確率 ≥ 0.5 | 注文番号の欄 |
| 担当部署が技術サポート | エラーコード・ご利用環境の欄 |
| 担当部署が配送 | 注文日・配送先の郵便番号の欄 |
| 緊急度スコア ≥ 2、または怒っている確率 ≥ 0.7 | 優先対応窓口の案内と折り返し電話番号の欄 |
| 怒っている確率 ≥ 0.5(優先対応時) | お詫びの一文 |

Claude は確率を返さないので、`noul` は 1(はい)か 0(いいえ)として同じしきい値で扱う。
送信ボタンはデモ用で、振り分け先を表示するだけ(実際には送らない)。

## 判定の鮮度表示

判定がどの入力に対するものかを覚えておき、今の入力と比べる。

- 同じなら「最新の入力に追いついている」
- 今の入力が判定時の入力の続きなら「N文字前の入力に対する判定」
- それ以外(削除や書き換え)は「古い入力に対する判定」

## 自動入力

発表中に打ち込まなくて済むよう、サンプル文を 60ms/文字 で入力する。

1. 二重請求(請求・返金・怒り → 注文番号欄と優先窓口が出る)
2. ログイン不可(アカウント or 技術サポート)
3. 配送
4. 途中で話が変わる(「ログインできない」→「解決した、請求書を再発行して」で判定が切り替わる)

## 計測結果(ローカル、Claude Haiku 4.5)

「途中で話が変わる」を自動入力したとき:

| 時点 | Jev | Claude Haiku |
|---|---|---|
| 入力開始から約1.8秒 | 7文字遅れ | 26文字遅れ |
| 入力完了後 | 判定11回・平均 286ms | 判定4回・平均 999ms |

どちらも最終的には「請求・支払い」に切り替わった。Jev の確信度は 98%。

### 3列にした後(本物の API、「配送」を自動入力、Opus は effort low)

|---|---|---|
| Jev | 9回 | 290ms |
| Claude Haiku 4.5 | 3回 | 1,238ms |
